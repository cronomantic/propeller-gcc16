# propgcc-16

A GCC 16.2.0 C toolchain for the Parallax Propeller 1 (P8X32A): the
Propeller back end of [propgcc](https://github.com/dbetz/propeller-gcc)
(David Betz, GCC 6) forwarded to GCC 16.2.0 by
[David-EIPI/propeller-gcc16](https://github.com/David-EIPI/propeller-gcc16),
over propgcc's binutils, C library, loader and OpenSpin.
[`CHANGES.md`](CHANGES.md) lists what differs from the GCC 6 propgcc
(bug fixes, new instruction patterns, optimisations).  As the port's own
README says, its patches and `CHANGES.md` were generated by an AI model
following its author's prompts, and tested by comparison with the GCC 6
propgcc.

This fork keeps the toolchain buildable and maintainable on its own:

- the **back end lives here as source files** (`backend/`), with its
  history: the GCC 6 files as imported, then the GCC 16 port applied on
  top, then whatever changes follow.  Only the registration of the target
  in GCC itself is a patch (`patches/gcc-16.2.0/`);
- the rest of the toolchain is in **submodules pinned to the commits it
  was built and tested with** (`deps/`), in forks next to this
  repository;
- one script builds everything (`build.sh`), and `tests/` checks the
  result.

## Layout

| Path | What |
| ---- | ---- |
| `backend/gcc/config/propeller/` | The compiler back end (`propeller.cc`, `propeller.md`, ...) |
| `backend/gcc/common/config/propeller/` | Target hooks shared with the driver |
| `backend/libgcc/config/propeller/` | libgcc's Propeller part: startup code, kernels, runtime helpers |
| `patches/gcc-16.2.0/` | `config.sub`, `gcc/config.gcc`, `libgcc/config.host`: the target registered in GCC |
| `deps/binutils-propeller` | Assembler, linker and binary utilities (totalspectrum, 2017) |
| `deps/proplib` | The C library (totalspectrum, 2016) |
| `deps/propeller-load` | The board loader (dbetz, 2016) |
| `deps/OpenSpin` | The Spin compiler, used by the loader (Parallax, 2018) |
| `build.sh` | Builds and installs the whole toolchain |
| `tests/` | `run.sh`: every test in every memory model, run in an emulator if one is given |
| `tests/xmm/` | What runs the external-memory builds: image builder, boot program, SPI SRAM driver |
| `tests/torture/` | `run.py`: GCC's own `gcc.c-torture/execute` tests in the emulator |
| `emu/` | A Propeller 1 emulator (`p1run`) with an SPI SRAM, and the P1 ROM, to run the tests |
| `CHANGES.md` | The port's changes against propgcc's GCC 6 back end |

## Building

Prerequisites: a C and C++ compiler, `make`, `flex`, `bison`, `texinfo`,
`curl` or `wget`, and the GMP, MPFR and MPC development headers
(Debian/Ubuntu: `build-essential flex bison texinfo libgmp-dev
libmpfr-dev libmpc-dev`; Fedora: `gcc gcc-c++ make flex bison texinfo
gmp-devel mpfr-devel libmpc-devel`).

    git clone https://github.com/cronomantic/propeller-gcc16.git
    cd propeller-gcc16
    git submodule update --init
    ./build.sh

`build.sh` downloads `gcc-16.2.0.tar.xz` from ftp.gnu.org once (checked
against its SHA-256), grafts `backend/` onto it, applies `patches/`, and
builds binutils, the compiler and libgcc, the C library, OpenSpin and the
loader into `$PREFIX` (default `$HOME/propgcc-16`).  Work files and logs
go to `$WORK` (default `./work`); `JOBS` sets make's parallelism.  It
takes about 15-25 minutes.  The host programs are installed without their
debug information (about 140 MB instead of 1.1 GB); `KEEP_DEBUG=1` keeps
it.  The Propeller libraries are not stripped either way.  The external
memory drivers' Spin sources are installed too, in
`propeller-load/xmem-drivers`, for boot programs that include one.

    PREFIX=/opt/propgcc-16 WORK=/tmp/pg16 JOBS=8 ./build.sh
    export PATH=$HOME/propgcc-16/bin:$PATH

The installation is relocatable: the tools find their libraries relative
to their own directory, so the prefix can be copied or moved as a whole.
Everything is named `propeller-elf-*`, so it can sit next to an older
propgcc.

## Testing

    tests/run.sh

compiles and links `tests/bench.c`, `tests/regress.c`, `tests/align.c`
and `tests/heap.c` at `-O2` and `-Os` in the LMM, CMM, XMMC, XMM single, XMM split and XMM models.  With
the emulator of `emu/`, every build is run too and must report success:

    make -C emu
    P1RUN=emu/build/p1run tests/run.sh

`emu/` is a Propeller 1 emulator: the eight cogs instruction by
instruction with the chip's timing, the hub, the counters, and the ROM
(Parallax's, GPL-3.0, from its Verilog release: see `emu/rom/README.md`).
`p1run` boots a `.binary` as the chip does and prints what the program
sends on P30; `make -C emu test` checks the emulator against instruction
vectors generated with spinsim.

The external-memory builds (XMMC, XMM single, XMM split, XMM) run from
a 23LC1024 SPI SRAM that `p1run --spi-sram` puts on P0-P3 (/CS, SCK,
SI, SO).  `tests/xmm/mkxmm.py` turns the `.elf` into the SRAM image, as
propeller-load lays it out, and a boot program that starts the external
memory driver and the program's XMM kernel, as propeller-load's
`flash_loader2.spin` does.  The driver, `tests/xmm/sram_xmem.spin`, is
propeller-load's `spi_sram24_xmem.spin` with two changes: the kernel's
RAM space ($20000000) goes after the image, so that XMM and XMM split,
which use both spaces, do not write their data over their code; and /CS
rises after the mode register is written (the original leaves it low, and
the chip then ignores the first transfer).  `regress.c` checks the code generation
bugs that `CHANGES.md` lists as fixed (64-bit division, `float` to `double`, `__builtin_ctz`,
the new MOVS/MOVD/MOVI and ADDS/SUBS patterns); `align.c` that objects
aligned to more than 4 bytes (globals, statics, common, members, locals,
a function, up to 4096) land on aligned addresses; `heap.c` mixes
`malloc`, `aligned_alloc`, `realloc` and `free` at random and checks
every live block after each step.

### GCC's torture tests

    tests/torture/run.py --model lmm,xmmc --opt=-O2,-Os -j 8

runs GCC's `gcc.c-torture/execute` tests (1,692 self-checking programs,
from the GCC sources that `build.sh` unpacks into `work/`) in the
emulator; `--suite ieee` and `--suite builtins` run the 69 floating-point
and 59 library-call tests of its subdirectories, with what their `.exp`
and `.x` files add.  Each test is compiled for the model and level, linked with
`tests/torture/exit.c` (so `exit` and `abort` end with propgcc's serial
exit sequence, which `p1run` turns into its exit status) and run.  The
tests' DejaGnu directives (`dg-options`, `dg-require-effective-target`,
`dg-skip-if`...) are honoured; results and logs go to `work/torture`.
`tests/torture/known.txt` lists what is expected not to pass, with the
reason; the run fails on anything else.  In every model (LMM, CMM,
XMMC, XMM single, XMM split, XMM) at `-O0`, `-O2` and `-Os`, 1,649 to
1,669 pass; the rest do not fit in memory (up to 17, in LMM at `-O0`),
need what the target lacks (21), are known limitations (`__int128`,
nested functions in CMM) or are too slow for the time limit, mostly at
`-O0` from external memory (they pass with a longer `--seconds`).
`ieee` passes in full everywhere, `builtins` too apart from what does not
fit in LMM and object-size checks too slow for the limit from external
memory.  `--doubles 32` runs them with `-m32bit-doubles`, propgcc's
default (results apart, and `known-d32.txt` on top of `known.txt`): the
same, less two `ieee` tests whose data are beyond `float`'s range.  The whole matrix takes about 25 minutes on 8 cores.

## Continuous integration and binaries

`.github/workflows/build.yml` builds the toolchain on Linux (Ubuntu
24.04) and on Windows (MSYS2 UCRT64) on every push and pull request,
and runs `tests/run.sh` with `emu/`'s emulator; on Linux, also the
three torture suites in LMM at `-O2`.  Each run keeps the installed toolchain as an
artifact (`propgcc-16-linux-x86_64.tar.xz`,
`propgcc-16-windows-x86_64.zip`, with the UCRT64 runtime DLLs next to the
programs).  Pushing a tag `v*` publishes the Windows one as a GitHub
release, with a `SHA256SUMS` file.  There is no Linux release: that build
uses the system's GMP, MPFR and MPC libraries and needs a glibc as new as
the build machine's, so on Linux `build.sh` is the way to install it.

## Following the port upstream

David-EIPI/propeller-gcc16 publishes the back end as patches against the
GCC 6 files.  A new version of its `01-propeller-backend-gcc16.patch` is
the difference between the GCC 6 back end and the new one, so its
changes are brought in as the difference between its old and new
versions, applied to `backend/`:

    interdiff old/01-propeller-backend-gcc16.patch new/01-propeller-backend-gcc16.patch \
        | patch -p1 -d backend

(`interdiff` is in patchutils.)  `backend/` started as the import of the
GCC 6 files at `totalspectrum/gcc-propeller` b4f45a4, followed by
upstream's `0a7bf91` version of the patch, so `git log backend/` shows
each step.

## Using

    propeller-elf-gcc -Os -mlmm -o hello.elf hello.c
    propeller-load -Dclkfreq=80000000 -Dclkmode=XTAL1+PLL16X -p /dev/ttyUSB0 -r -t hello.elf

Memory models: `-mlmm` and `-mcmm` (code in hub RAM), `-mcog` (code in a
cog), `-mxmmc` (code in external memory, data in hub RAM), `-mxmm-single`
and `-mxmm-split` (code and data in external memory, through a cache and
a board-specific external memory driver).
